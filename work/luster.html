LUSTER: one token layer, three brands

Role Design system designer, one of sevenCourse Design Systems and Tokens with AI, by Osama EldreinyTools Figma variables, HTML and CSS
The team's case study site. Click to open it.
The short version

LUSTER was the final project of Osama Eldreiny's Design Systems and Tokens with AI course, built by a team of seven. It's a multi-brand system with three brands, light and dark modes and seven theming switches, mirrored one-to-one between Figma variables and production CSS. Like everyone on the team, I planned and mind-mapped the tokens for a set of components, so the whole system used one naming structure. It's where I learned the architecture I later used to build a white-label system on my own.

Why a team project is here

It sits between my first design system and my third. The first taught me how to lead a team and keep a system running. LUSTER took me deeper into token architecture. On the third, I built that architecture alone and pushed it further.

The idea

Most companies add a second brand by copying the component library and recolouring it. Now there are two libraries to maintain, and they drift apart the moment anything changes. LUSTER does it the other way: every brand shares one set of components, and only the tokens change.

Three layers of tokens

  1. Options: raw values like colour palettes, spacing, sizes, radii and fonts. No decisions yet.
  2. Semantic: what a value means, like background, text, border or error. Each brand and mode remaps this layer.
  3. Component: what each component uses, such as menuItem/hover/bg. It always points to a semantic token, never a raw value.

Seven switches

Brand: Diamond, Amber, OpalLight and darkEnglish LTR and Arabic RTLSerif or sans typographyDensityCorner radiusShadow

Each switch is its own Figma variable collection, so you can change one without touching the others.

19 components

ButtonToggleRadio buttonInput fieldAvatarLogoPalettesAlertList itemsMenu itemChoose cardImageMeeting cardCardNavbarTabsFooterHeaderPagination

Every component has a live themed preview, a token table that matches its Figma variable path exactly, and code to copy.

My part

Before anyone built components, each of us took a set of them and planned their tokens: mapping every property (background, text, border, spacing, states) to the right semantic token, and agreeing one naming pattern across the whole system. That shared structure is what made it possible for seven people to build one library that reads as if one person made it.

What I took into my next system

  • Components never touch raw values. I used the same three tiers on my white-label system.
  • Each switch is independent. LUSTER had seven; my white-label system has nine.
  • Design and code use the same names. On my next system I agreed token names and the CSS structure directly with developers.
